# ВышКат — учёт парка кикшеринга

Консольное приложение для учёта транспорта и инвентаря сервиса «ВышКат».

Проект разработан в рамках домашнего задания по конструированию программного обеспечения. Основные задачи — применение принципов SOLID, внедрение зависимостей (DI) и проверка поведения приложения с помощью юнит-тестов.

## Возможности

Приложение поддерживает:

- добавление транспортных средств в парк с предварительным техосмотром;
- принятие или отклонение транспорта в зависимости от реализации техосмотра;
- учёт инвентаризируемых объектов, включая транспорт и вещи;
- контроль уникальности инвентарных номеров;
- формирование отчёта о количестве транспортных средств;
- расчёт суммарного суточного энергопотребления парка;
- вывод транспорта, подходящего для новичков;
- вывод полной инвентаризации с названиями объектов и инвентарными номерами.

Для новичков подходит транспорт с показателем простоты не менее 6 из 10. Энергопотребление учитывается для объектов, реализующих интерфейс `iEnergyCustomer`.

## Структура проекта

Основные компоненты приложения:

- `Models` — модели предметной области, интерфейсы и класс `Park`.
- `Services/ParkReplenishment.cs` — добавление объектов в парк и взаимодействие с техосмотром.
- `Services/Implementations` — реализации техосмотра и сервиса формирования отчётов.
- `Program.cs` — точка входа и настройка зависимостей.
- `kpo_vishkat.Tests` — проект юнит-тестов.

### Модель предметной области

`iInventoryItem` задаёт общий контракт для объектов, которые учитываются на балансе и имеют инвентарный номер. Было решено, что любой объект должен иметь инвентарный номер для учета.

`iTransport` описывает транспортные средства, включает характеристику простоты для новичка.

`iEnergyCustomer` описывает объекты, потребляющие энергию, и предоставляет значение суточного энергопотребления.

`Park` хранит все инвентаризируемые объекты в одной коллекции. Для получения транспорта и энергопотребляющих объектов используются отдельные представления через LINQ. Благодаря этому один объект не требуется хранить в нескольких коллекциях.

## Техосмотр

Интерфейс `iServiceCenter` отделяет решение о приёмке транспорта от логики управления парком.

В проекте предусмотрены три реализации:

- `AlwaysAcceptServiceCenter` — принимает любой ненулевой объект транспорта.
- `AlwaysDeclineServiceCenter` — отклоняет любой ненулевой объект транспорта.
- `SimplicityDrivenServiceCenter` — принимает транспорт, если его простота не меньше 3.

Текущий порог 3 используется для демонстрации альтернативной политики техосмотра. Он не заменяет отдельное требование отчёта для новичков, где порог составляет 6.

`ParkReplenishment.TryAddTransport()` обращается к переданному `iServiceCenter`. Если транспорт отклонён, метод возвращает `false` и не добавляет его в парк. При успешной проверке транспорт добавляется через `Park.AddItem()`.

## Отчёты

Каждая реализация отчёта является реализацикй интерфейса `iReportService` и отвечает за отдельную задачу:

- `TransportCountReportService` — количество транспортных средств.
- `EnergyConsumptionReportService` — суммарное суточное энергопотребление.
- `SimplicityReportService` — список транспорта, подходящего для новичков.
- `InventoryReportService` — полная инвентаризация имущества.

Отчёты используют данные из `Park` и не дублируют хранение объектов. Такое разделение позволяет добавлять новые варианты отчетности и изменять старые, без изменения других отчетов.

## Принципы SOLID

### SRP — принцип единственной ответственности

Применён наиболее явно.

- `Park` отвечает за хранение имущества и уникальность инвентарных номеров.
- `ParkReplenishment` отвечает за сценарий пополнения парка и вызов техосмотра.
- Каждая реализация `iReportService` отвечает за один конкретный отчёт.
- Каждая реализация `iServiceCenter` содержит отдельную политику приёмки.

Изменение формата одного отчёта не требует изменения остальных отчётов или модели парка.

### OCP — принцип открытости/закрытости

Новые варианты техосмотра можно добавлять отдельными реализациями `iServiceCenter`, не меняя `ParkReplenishment`.

Аналогично, новые отчёты можно реализовать через `iReportService`, а новые виды транспорта — через `iTransport`.

При этом добавление нового типа транспорта может потребовать регистрации его создания в консольном интерфейсе.

### LSP — принцип подстановки Барбары Лисков

Реализации `iServiceCenter` можно подставлять вместо друг друга: каждая предоставляет метод `Accept()` и возвращает решение о приёмке.

Различается политика принятия решения, но `ParkReplenishment` продолжает работать через общий интерфейс.

### ISP — принцип разделения интерфейса

Интерфейсы разделяют разные возможности: инвентаризацию - `iInventoryItem`, транспорт - `iTransport` и потребление энергии `iEnergyCustomer`.

Это позволяет не добавлять объектам свойства и методы, которые им не нужны.

### DIP — принцип инверсии зависимостей

`ParkReplenishment` зависит от абстракции `iServiceCenter`, а не от конкретного класса техосмотра.

Это позволяет использовать разные политики приёмки и подменять их в тестах без изменения бизнес-логики.

## Осознанные ограничения

В проекте не вводится отдельная иерархия базовых классов для каждого вида имущества: общей абстракции `iInventoryItem` достаточно для текущих требований.

`Park` хранит конкретную коллекцию объектов, а не зависит от отдельного репозитория или универсального хранилища. Для небольшого консольного приложения этого достаточно.

`ParkReplenishment` не имеет разделения на интерфейс и реализацию (нарушен OCP), т.к. изменение и модификация данного компонента не предполагается.

Консольный интерфейс может знать о конкретных типах транспорта, которые пользователь может создать. Если видов транспорта станет много, создание объектов можно будет вынести в отдельный механизм регистрации или фабрику.

## Внедрение зависимостей

Зависимости создаются и передаются компонентам через конструкторы. В точке входа приложения настраивается DI-контейнер.

Для отчётов используется общий интерфейс `iReportService`, что позволяет получать набор реализаций и выводить их результаты без необходимости связывать интерфейс с конкретными классами отчётов.

Для проверки подмены техосмотра в тестах можно передать в `ParkReplenishment` любую реализацию `iServiceCenter`, включая тестовую заглушку.

## Тестирование

Юнит-тесты проверяют поведение отдельных компонентов.

Основные сценарии:

- добавление объекта в парк;
- отклонение повторяющегося инвентарного номера;
- фильтрация транспорта и энергопотребляющих объектов;
- принятие и отклонение транспорта разными реализациями техосмотра;
- отказ от добавления транспорта после отрицательного результата техосмотра;
- проверка порогового значения простоты для техосмотра;
- формирование всех четырёх отчётов;
- проверка правила простоты не менее 6 для транспорта, предназначенного новичкам;
- подмена реализации техосмотра в тестах.

## Запуск

Для сборки решения из каталога, в котором находится файл решения `.slnx`, выполните:

```bash
dotnet build
```

Для запуска консольного приложения:

```bash
dotnet run --project kpo_vishkat
```

Для запуска юнит-тестов:

```bash
dotnet test
```

Если проект расположен в другой папке, укажите путь к соответствующему `.csproj`.

## Возможности расширения

### Новый вид транспорта

Новый тип транспорта должен реализовать `iTransport`. Если он потребляет энергию, дополнительно реализуется `iEnergyCustomer`.

Основная логика хранения и формирования отчётов при этом остаётся прежней, если новый тип соблюдает контракты интерфейсов.

## Использование ИИ

При разработке проекта ИИ использовался как вспомогательный инструмент для обсуждения архитектуры, подготовки примеров юнит-тестов и оформления README.
